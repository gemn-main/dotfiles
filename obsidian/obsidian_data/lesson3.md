## 0. Карта: где мы находимся

Любое решение ML-задачи — это цепочка. Вот вся цепочка целиком, чтобы вы видели, куда ведёт каждый урок:

```
 загрузка данных
       │
       ▼
 подготовка X и y  ──────────── урок 1, 2
       │
       ▼
 ┌─────────────────────────────────────────────┐
 │  ВАЛИДАЦИЯ: cross_val_score(модель, X, y)   │  ◄── УРОК 3 (мы здесь)
 │  «насколько хороша эта модель?»             │
 └─────────────────────────────────────────────┘
       │            ▲
       │            │ каждый раз, когда мы пробуем что-то новое:
       │            │   - другую модель      (урок 4–5)
       │            │   - новые признаки     (урок 6)
       │            │   - новые параметры    (урок 7, Optuna)
       ▼            │
 выбрали лучший вариант (с самой низкой ошибкой)
       │
       ▼
 обучили на ВСЕХ данных train  →  предсказали test  →  submission.csv
```

**Главная мысль:** валидация — это **линейка**. Всё остальное (модели, признаки, Optuna) — то, что мы этой линейкой измеряем. Поэтому шаблон из этого урока вы будете использовать в каждом следующем.

## 1. Зачем вообще нужна валидация

Правильных ответов проверочного набора у вас нет, их знает только проверяющая система. Но пробовать десятки вариантов, отправляя каждый на проверку, нельзя: попыток мало, а оценка идёт на 20% объектов и шумная.

Значит, нужен способ узнать качество **самим**. Идея простая: часть train **прячем** от модели, обучаем на остальном, проверяем на спрятанной части. Ошибка на спрятанных данных честная, потому что модель их не видела.

### Что будет, если проверять на тех же данных, где училась

Модель может не обобщать, а просто **запоминать**. Пример из реальных данных (дерево решений без ограничений глубины):

| Где считаем ошибку | RMSE |
|---|---|
| на данных, где училась | **0.0000** (идеально!) |
| на спрятанных данных | **0.3278** (хуже, чем «всегда предсказывать среднее»: 0.2969) |

Если бы вы смотрели только на первую строку, решили бы, что модель идеальна. Это называется **переобучение**.

## 2. Шаблон по строкам

Вот весь шаблон. Дальше разбираем его по частям.

```python
import numpy as np
import pandas as pd
from sklearn.model_selection import KFold, cross_val_score
from sklearn.pipeline import make_pipeline
from sklearn.impute import SimpleImputer
from sklearn.tree import DecisionTreeRegressor

# --- данные ---
df = pd.read_csv("train.csv")
y = np.log1p(df["yield_t_ha"])
X = df.drop(columns="yield_t_ha").select_dtypes("number")
X = X.replace([np.inf, -np.inf], np.nan)

# --- модель ---
model = make_pipeline(
    SimpleImputer(strategy="median"),
    DecisionTreeRegressor(max_depth=3, random_state=0),
)

# --- валидация ---
cv = KFold(5, shuffle=True, random_state=42)
scores = cross_val_score(model, X, y, cv=cv, scoring="neg_root_mean_squared_error")

print(-scores)          # [0.272 0.3173 0.3058 0.2922 0.2841] ошибка на каждом из 5 фолдов
print(-scores.mean())   # 0.2943
```

### 2.1. Блок «данные»

| Строка | Что делает | Зачем |
|---|---|---|
| `y = np.log1p(df["yield_t_ha"])` | берёт столбец цели и берёт от неё `log(1+x)` | метрика RMSLE равна обычному RMSE на логарифмах (урок 2) |
| `df.drop(columns="yield_t_ha")` | убирает цель из таблицы | **цель нельзя оставлять среди признаков**, иначе модель подсмотрит ответ |
| `.select_dtypes("number")` | оставляет только числовые столбцы | текст мы научимся обрабатывать на уроке 4 |
| `.replace([np.inf, -np.inf], np.nan)` | заменяет бесконечности на пропуски | в данных спрятано 9 значений `inf`; `isna()` их не видит, а многие модели от них падают |

### 2.2. Блок «модель» и что такое Pipeline

`make_pipeline(A, B)` склеивает шаги в одну «машину». У неё два главных действия:

```
model.fit(X_train, y_train)       model.predict(X_new)
        │                                 │
        ▼                                 ▼
 1. Imputer ЗАПОМИНАЕТ медианы     1. Imputer заполняет пропуски
    по X_train и заполняет            ТЕМИ ЖЕ медианами
    пропуски                       2. Дерево предсказывает
 2. Дерево УЧИТСЯ на               
    заполненных данных              
```

**Главное:** медианы запоминаются по **train-части**, а на проверочных данных используются те же самые числа. Это защита от утечки (раздел 4).

Что значат параметры:
- `strategy="median"` — пропуск заменяется медианой столбца;
- `max_depth=3` — дерево задаёт не больше 3 вопросов подряд. Чем больше глубина, тем легче запомнить данные (переобучение);
- `random_state=0` — фиксирует случайность, чтобы результат повторялся.

### 2.3. Блок «валидация»: что делает `cross_val_score`

```python
cv = KFold(5, shuffle=True, random_state=42)
```
- `5` — на сколько частей делим данные;
- `shuffle=True` — перед делением перемешиваем строки (иначе части могут оказаться «по порядку», например, по регионам);
- `random_state=42` — фиксируем перемешивание, чтобы деление не менялось от запуска к запуску. **Пока вы сравниваете модели, `cv` должен быть одинаковым**, иначе сравнение нечестное.

А `cross_val_score(...)` делает вот что:

```
Данные: [ A | B | C | D | E ]   (5 частей по ~817 строк)

Фолд 1: учим на B C D E  → проверяем на A → ошибка_1
Фолд 2: учим на A C D E  → проверяем на B → ошибка_2
Фолд 3: учим на A B D E  → проверяем на C → ошибка_3
Фолд 4: учим на A B C E  → проверяем на D → ошибка_4
Фолд 5: учим на A B C D  → проверяем на E → ошибка_5

Возвращает: [ошибка_1, ошибка_2, ошибка_3, ошибка_4, ошибка_5]
```

Это эквивалентно ручному циклу. Для понимания, вот то же самое без магии (запускать необязательно, главное увидеть, что внутри нет ничего волшебного):

```python
errors = []
for train_idx, valid_idx in cv.split(X):                # номера строк для каждого фолда
    model.fit(X.iloc[train_idx], y.iloc[train_idx])     # учим на 4 частях
    pred = model.predict(X.iloc[valid_idx])             # предсказываем на пятой
    errors.append(np.sqrt(np.mean((y.iloc[valid_idx] - pred) ** 2)))
```

Пять моделей создаются и обучаются заново, их ответы друг на друга не влияют. Итоговой «обученной модели» после `cross_val_score` у вас **нет**: это только измерение.

### 2.4. Почему `scoring="neg_root_mean_squared_error"` со знаком минус

В sklearn принято, что **больше = лучше**. Ошибка же должна быть меньше. Поэтому sklearn возвращает ошибку со знаком минус (−0.29 лучше, чем −0.35), а мы перед печатью ставим `-` и снова получаем обычное положительное число.

Так как `y` уже в логарифме, эта RMSE и есть наша RMSLE.

### 2.5. Как читать результат

```
[0.272  0.3173 0.3058 0.2922 0.2841]   ← ошибка по фолдам
0.2943         ← среднее: это и есть «качество модели»
```

Ориентиры (RMSE на логарифмах, чем меньше, тем лучше):

| Что | Ошибка |
|---|---|
| «всегда предсказывать среднее» (`DummyRegressor`) | 0.3053 |
| дерево глубины 3 | 0.2943 |
| LightGBM (раздел 5) | 0.2209 |
| LightGBM после Optuna (раздел 6) | 0.2175 |

Эти числа показывают вашу цель: **любая модель должна побеждать нижнюю строчку**. Если нет, она бесполезна.

## 3. Три способа проверки: когда какой

| Способ | Как работает | Когда использовать |
|---|---|---|
| **Holdout** (`train_test_split`) | один раз делим 80/20 | быстрая проверка идеи; оценка шумная |
| **K-Fold** (`KFold`) | 5 делений, среднее | **основной вариант для регрессии** |
| **StratifiedKFold** | как K-Fold, но сохраняет доли классов | **только классификация**; на непрерывной цели выдаёт ошибку |

Холдаут шумный. Один и тот же алгоритм на разных делениях дал 0.3094, 0.3098 и 0.3155. Поэтому для решений берём K-Fold.

## 4. Утечка данных: главная ловушка

**Утечка** — когда в обучение попадает информация, которой в реальности не будет. Оценка получается красивой, а на настоящем test результат разочарует.

### Пример 1. Дублирование строк (мы делаем это специально)

Мы продублировали все строки, так что каждая попала и в train, и в valid. Дерево без ограничений показало **0.1557** вместо честных **0.3404**. Модель не стала умнее, она просто увидела те же ответы.

### Пример 2. Подготовка данных до разбиения

Неправильно:
```python
X = X.fillna(X.median())      # медиана посчитана по ВСЕМ строкам, включая будущие valid
cross_val_score(DecisionTreeRegressor(), X, y, cv=cv)
```
Правильно:
```python
model = make_pipeline(SimpleImputer(strategy="median"), DecisionTreeRegressor())
cross_val_score(model, X, y, cv=cv)    # медиана считается заново внутри каждого фолда
```
В первом случае информация о проверочных строках подмешалась в обучающие через медиану. Эффект здесь небольшой, но с более сложной подготовкой (масштабирование, кодирование по цели) он бывает огромным. **Правило: всё, что «обучается» на данных, живёт внутри Pipeline.**

## 5. Шаблон растёт: меняем только модель

Вся ценность шаблона в том, что при замене модели остальной код не меняется. Берём LightGBM (мы использовали его в самом первом решении):

```python
import lightgbm as lgb

model = lgb.LGBMRegressor(n_estimators=300, learning_rate=0.03, verbose=-1, random_state=0)
# cv, cross_val_score — те же самые строки
scores = cross_val_score(model, X, y, cv=cv, scoring="neg_root_mean_squared_error")
print(-scores.mean())     # 0.2209
```

Результат упал с 0.2943 до **0.2209**: бустинг намного сильнее одного дерева. Заметьте, что `SimpleImputer` не понадобился: LightGBM сам умеет работать с пропусками (поэтому `inf` мы всё равно заменяем на `nan`).

Параметры:
| Параметр | Что значит |
|---|---|
| `n_estimators=300` | сколько деревьев строить (каждое исправляет ошибки предыдущих) |
| `learning_rate=0.03` | шаг обучения; меньше шаг — точнее, но нужно больше деревьев |
| `verbose=-1` | не печатать служебные сообщения |

## 6. Optuna: как автоматически подбирать параметры

### Идея
У LightGBM десятки параметров: сколько листьев, какая доля строк, какая регуляризация. Перебирать вручную долго. **Optuna** делает это за нас: пробует разные значения, смотрит ошибку и каждый раз выбирает следующую пробу умнее (по результатам предыдущих).

### Где здесь валидация
Ошибку для каждой пробы считает **наш шаблон** из раздела 2. Optuna — это внешний цикл, а `cross_val_score` — внутренняя линейка.

```
Optuna: «попробуем num_leaves=24, learning_rate=0.07...»
   │
   ▼
 строим LightGBM с этими параметрами
   │
   ▼
 cross_val_score → ошибка (например, 0.2190)   ← наш шаблон
   │
   ▼
Optuna запоминает: «такие параметры дали 0.2190»,
подбирает следующую пробу и повторяет
```

### Код

```python
import optuna

def objective(trial):
    params = dict(
        n_estimators=300,
        learning_rate=trial.suggest_float("learning_rate", 0.01, 0.1, log=True),
        num_leaves=trial.suggest_int("num_leaves", 4, 64),
        min_child_samples=trial.suggest_int("min_child_samples", 5, 60),
        subsample=trial.suggest_float("subsample", 0.5, 1.0),
        subsample_freq=1,
        colsample_bytree=trial.suggest_float("colsample_bytree", 0.4, 1.0),
        reg_lambda=trial.suggest_float("reg_lambda", 1e-3, 10, log=True),
        verbose=-1,
        random_state=0,
    )
    model = lgb.LGBMRegressor(**params)
    scores = cross_val_score(model, X, y, cv=cv, scoring="neg_root_mean_squared_error")
    return -scores.mean()          # Optuna будет ЭТО минимизировать

study = optuna.create_study(direction="minimize")
study.optimize(objective, n_trials=20)

print(study.best_value)     # 0.2175
print(study.best_params)    # лучшие найденные параметры
```

### Разбор по частям

| Что | Значение |
|---|---|
| `objective(trial)` | функция, которая получает «пробу» и возвращает **число, которое надо минимизировать** (у нас это ошибка) |
| `trial.suggest_float("learning_rate", 0.01, 0.1, log=True)` | «предложи значение от 0.01 до 0.1». `log=True` значит, что значения пробуются равномерно в логарифмической шкале, это правильно для параметров, которые отличаются в разы (0.01, 0.03, 0.1) |
| `trial.suggest_int("num_leaves", 4, 64)` | то же, но целое число |
| `direction="minimize"` | мы ищем минимум ошибки (если бы метрика была «чем больше, тем лучше», писали бы `"maximize"`) |
| `n_trials=20` | сколько проб сделать. Для настоящей задачи берут 50–200 |
| `study.best_params` | словарь лучших параметров |

Зачем `n_estimators=300` зафиксирован: иначе Optuna будет делать модели разных размеров и перебор усложнится. Число деревьев подбирают отдельно (early stopping, урок 5).

### Результат на ваших данных
За 20 проб ошибка снизилась с **0.2209 до 0.2175**. Прирост небольшой. Это нормально: настройка параметров обычно даёт ещё 1–3%, а основной скачок давала замена модели и признаки.

### Осторожно: Optuna подгоняется под валидацию
Чем больше проб, тем больше шанс, что параметры «случайно» хорошо подошли именно к этому делению на фолды. Поэтому итоговая оценка 0.2175 немного оптимистична. На настоящем test ошибка чуть выше. Это не повод не пользоваться Optuna, но не удивляйтесь небольшой разнице.

## 7. Финал: от валидации к файлу для отправки

`cross_val_score` ничего не обучает «для использования». Он только измеряет. Для submission делаем отдельный шаг: **обучаем лучшую модель на ВСЕХ данных train и предсказываем test.**

```python
# 1. лучшая модель из Optuna
best_model = lgb.LGBMRegressor(
    n_estimators=300, subsample_freq=1, verbose=-1, random_state=0,
    **study.best_params,
)

# 2. обучаем на всех данных (валидация закончилась, прятать больше нечего)
best_model.fit(X, y)

# 3. готовим test ТАК ЖЕ, как train
test = pd.read_csv("test.csv")
X_test = test[X.columns]                                   # те же столбцы в том же порядке
X_test = X_test.replace([np.inf, -np.inf], np.nan)         # та же обработка inf

# 4. предсказание и возврат из логарифма
pred = np.expm1(best_model.predict(X_test))                # expm1 — обратное к log1p

# 5. сохраняем
sub = pd.DataFrame({"id": test["id"], "yield_t_ha": pred})   # названия столбцов смотрите в примере из задачи
sub.to_csv("submission.csv", index=False)
```

Типичные ошибки на этом шаге:
| Ошибка | Последствия |
|---|---|
| забыли `np.expm1` | предсказания в логарифмах (число 3.5 вместо 33), оценка ужасная |
| test обработан не так, как train | модель получает данные, на которых не училась |
| столбцы test в другом порядке | модель путает признаки |
| забыли `fit` на всех данных | предсказываем моделью, которая видела только 80% |

## 12. Итог урока

1. Качество проверяют на данных, которых модель не видела.
2. Одному делению верить нельзя, берут K-Fold.
3. Всё, что обучается на данных, кладут внутрь Pipeline, это защита от утечки.
4. Валидация — линейка: модели, признаки и Optuna работают поверх неё.
5. После валидации и подбора модель **заново обучают на всех данных** и только потом предсказывают test.
6. Если результат слишком хорош, сначала подозревайте утечку.
